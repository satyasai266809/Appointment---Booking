# Appointment Booking (conflict-safe booking and cancellation)

A small in-memory service slice (no starter project was supplied). Java 21, Maven, JUnit 5.

## Setup and run

Requirements: JDK 21+ and Maven 3.9+.

```bash
mvn test        # compile and run all 28 tests
```

Usage (see `AppointmentServiceTest` for examples):

```java
var service = new AppointmentService(new InMemoryAppointmentRepository());
BookingResult r = service.book("dr-a", "2030-01-01T09:00:00Z", "2030-01-01T10:00:00Z");
CancelResult  c = service.cancel(r.appointment().id());
```

## Booking invariant

For any provider, no two ACTIVE appointments overlap. An appointment occupies the half-open interval
`[start, end)`, so two intervals overlap iff `a.start < b.end && b.start < a.end`. Adjacent
appointments (one ends exactly when the next starts) are allowed. Cancelled appointments are ignored.

## Assumptions

- All timestamps are ISO-8601 UTC instants and must end in `Z` (e.g. `2030-01-01T09:00:00Z`). Offsets
  such as `+02:00`, local times and date-only values are rejected.
- Duration must be positive (`end > start`); there is no minimum, maximum or granularity.
- The appointment id is generated by the service (UUID); callers do not supply it.
- Provider identity is an opaque non-blank string compared exactly (case- and whitespace-sensitive, no
  trimming); providers are not validated against a directory.
- Booking in the past is allowed (no clock dependency).
- Rejections are returned as result objects (`CONFLICT`, `INVALID_INPUT`, `NOT_FOUND`,
  `ALREADY_CANCELLED`), not thrown. Failed requests never modify stored data.
- Cancelled appointments are kept (state `CANCELLED`) rather than deleted, so a repeat cancel can be
  distinguished from a missing id.

## Limitations and follow-up risks

- Concurrency safety is a single in-process lock: correct for one JVM, not across several instances.
  A real database needs a transaction plus an exclusion constraint (e.g. PostgreSQL `tstzrange`
  with `EXCLUDE USING gist`) or `SELECT ... FOR UPDATE` on the provider row.
- One global lock serialises all bookings, including those for different providers. Per-provider
  locking is a straightforward optimisation if throughput matters.
- `findActiveByProvider` scans linearly; an interval index or sorted structure would be needed at scale.
- No persistence: data is lost on restart.
- No authorisation: anyone can cancel any appointment id.
